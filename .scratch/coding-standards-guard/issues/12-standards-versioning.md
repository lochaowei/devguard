# 預設標準的版本發佈與專案升級方式

Type: grilling
Status: resolved
Blocked by: 05, 07

## Question

預設標準放在哪裡、如何版本化發佈（跟 CLI 綁在一起還是獨立發佈）？專案如何鎖定所用版本、如何得知有新版、升級時如何呈現差異？

> 來自「工具版本權威與一致性檢查」的備註：預設標準中包含每個工具允許的版本範圍，以及 golangci-lint 的指定版本（binary 放在內部 Scoop bucket）。升級預設標準時，這些範圍也會跟著變動，因此要考慮專案升級標準時，鎖定的工具版本如何一併升級。

## Answer

- **發佈**：預設標準**內建在 CLI 中**。每個 CLI 版本都附帶歷來所有的標準版本，宣告中的 `standard: team@x.y.z` 不需要連網就能解析。調整標準就要發佈新版 CLI，開發者執行 `scoop update <cli>` 取得。標準的原始檔另外放在一個內部 repo。
- **版本號的意義**：依「是否會讓原本通過的專案變成失敗」區分。
  - **major**：可能讓原本通過的專案失敗。例如收緊、新增規則、工具版本範圍改成不相容的範圍。
  - **minor**：不會讓任何專案失敗。例如新增選用項目、新增允許的替代工具、放寬、在相容範圍內擴大工具版本範圍。
  - **patch**：只修改說明，不影響行為。
- **專案宣告寫確切版本**，例如 `team@1.2.0`，確保同一個 commit 在任何機器、任何時間的檢查結果都一樣。有 minor 或 patch 更新時，doctor 會直接建議升級。
- **CLI 支援的標準版本**：目前的 major 版本與前一個 major 版本中的所有版本。
  - 宣告的版本比 CLI 內建的更新：回報錯誤，提示執行 `scoop update <cli>`。
  - 宣告的版本太舊、已經不在 CLI 中：回報錯誤，提示升級標準。
- **升級指令** `<cli> standard upgrade [目標版本]`：
  - 預設只預覽，列出四類資訊：標準項目的差異、對本專案的影響（哪些覆寫變得多餘、哪些會成為新的偏離或錯誤）、需要調整的工具版本、需要執行的套件管理指令。
  - 加上 `--apply` 才會修改宣告與工具設定檔，並透過內部鏡像執行套件管理指令。
- **強制升級**：團隊可以把某個標準版本標為棄用，並設定截止日。截止日之前 doctor 只顯示提示，之後檢查會回報錯誤。
- **範圍外**：誰能修改標準、審核流程與發佈頻率屬於組織流程，由團隊自訂。
